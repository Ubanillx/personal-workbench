# 助理任务可见范围与优先级排序：实施记录

状态：已按用户确认方案实施并完成验证（2026-10-13）。用户通过选项确认规则后明确授权“按照该方案实施”。

本文记录本次需求的分析结果，不覆盖 `ACCOUNTS_AND_ORGS.md` 中已确认的现行规则。

## 1. 原始需求

各个助理只能看到自己发布的任务和上级分派的任务，可以选择排序优先级，按优先级显示。先分析代码，再与用户对齐细节。

## 3. 用户已确认的核心规则（2026-10-13）

1. **助理范围**：仅普通成员 `member`；组织管理者保留本组织管理视图，私密任务仍按现行规则限制。管理员保持现行全局范围。
2. **分派认定**：在组织边界内，本人发布或当前负责人为本人即可见，即 `created_by = 本人 OR owner_id = 本人`；不新增直属上级关系。普通成员对其他人的非私密任务不再有可见权。
3. **优先级含义**：仅选择按现有 `P0/P1/P2` 排序，不修改任务等级，也不新增独立个人任务等级。

用户通过可点击选项提交上述选择，随后明确授权实施；本记录保留这些核心规则。

## 4. 用户已确认的排序细节（2026-10-13）

1. **默认排序**：仅普通成员在任务页默认 `P0 → P1 → P2`；管理员和组织管理者保留最近更新时间降序。所有角色均可选择优先级排序，也保留现有其他排序方式。
2. **同优先级次序**：最近更新时间降序，最后按任务 ID 稳定排序。
3. **排序记忆**：仅保留当前 URL，刷新和翻页保留；从导航重新进入使用角色对应默认排序。不新增浏览器持久化或账号级偏好存储。

用户确认上述选择，并要求按方案实施。

## 5. 实施建议与边界

- 按已确认规则，仅收紧普通成员可见性，同时更新列表和单条任务的权限判据。
- 管理员及组织管理者保留现行查看范围，不能把组织管理视图解释为可查看他人私密任务。
- 优先级排序高优先级在前：`P0`、`P1`、`P2`；同级按更新时间降序，再按任务 ID 稳定排序。
- 排序必须在服务端分页之前执行。切换排序回到第一页，刷新和翻页保留 URL 中的排序条件。
- 角色默认排序仅在 URL 未指定有效排序时使用；用户明确选择其他有效排序时，以该选择为准。重置或从导航重新进入时回到角色默认排序。
- 仅增加按现有优先级排序，不改变任务等级，也不放开普通成员对全部任务元信息的编辑权限。
- 按已确认的当前负责人规则，改派后若原负责人不是发布人，立即失去查看权；发布人仍受组织边界限制，不能因历史发布关系获得跨组织查看权。
- 现有进度和验收状态机不因排序变化而改变。

## 6. 实施时必须覆盖的入口

| 范围                         | 调整或核验要求                                                             |
| ---------------------------- | -------------------------------------------------------------------------- |
| 任务列表与 API               | `visibilityClauses()` 必须符合新规则，筛选不能扩大可见范围                 |
| 详情、评论、时间线及写操作   | `canView()`、`viewable()` 与列表规则一致；不可见任务不能通过 ID 访问或操作 |
| 首页、统计和回顾             | 使用同一任务可见范围；不能从数量或汇总中泄露不可见任务                     |
| 通知列表、未读数量及实时推送 | 核验新收件人和历史通知的可见性；改派后不能通过旧通知继续暴露任务内容       |
| 企微导入和预览               | 核验成员导入任务的归属；检查重复检测是否暴露不可见任务存在性               |
| 列表排序                     | 新增服务端优先级排序白名单及界面入口，处理同级稳定次序，不仅排序当前页     |
| 权限与界面说明               | 更新任务页和首页文案，避免继续声称组织内全部非私密任务对所有人可见         |

已确认不新增直属上级关系、独立个人任务等级或排序偏好存储。本次不计划新增数据库迁移，不修改已应用迁移，不删除、回填或重写历史任务数据。

## 7. 验收要求

- 助理能看到自己发布的任务及符合最终分派规则的任务；看不到其他助理的任务，包括非私密任务。
- 同组织不可见任务的详情、评论、时间线和写操作拒绝访问；跨组织按 ID 访问仍返回 404。
- 管理角色可见范围按最终确认执行；未加入组织的普通账号不能读取任何任务。
- 改派、归档、恢复和跨组织移动后，可见范围、统计及通知保持一致。
- 用混合 `P0/P1/P2`、同优先级并列及多页数据验证整体排序、升降序、刷新和翻页；非法排序参数不能进入 SQL。
- 排序不会修改任务优先级，也不会放宽普通成员对任务元信息、负责人、状态或验收的现行写权限。
- 更新 `tools/contract/cases.ts` 和 SSR 冒烟覆盖；先比较契约差异，确认有意变更后重录 golden。
- 功能实施后同步权限文档；API、数据模型及配置有变化时按仓库规则同步相应文档。
- 功能交付前运行 lint、typecheck、完整测试、build、antd lint 和 format check；当前草案不代表这些门禁已通过。

## 8. 实施结果

1. **权限统一**：新增 `app/lib/task-visibility.server.ts`，列表、详情、评论、时间线、统计、首页、写操作和企微去重均复用“同组织且本人发布或当前负责”的成员判据；跨组织仍返回 404。
2. **通知一致性**：历史通知按当前任务可见性过滤，未读数与列表共用查询；改派、隐私和组织移动触发 SSE `resync`，不会继续推送已不可见任务内容，历史记录不删除。
3. **服务端排序**：任务排序白名单新增 `priority`，在分页前按优先级、更新时间、任务 ID 排序；成员默认 P0→P1→P2，管理者和管理员保留更新时间倒序。URL 保留排序状态，重置回到角色默认值。
4. **文档与契约**：同步 `ACCOUNTS_AND_ORGS.md`、`ARCHITECTURE.md`、README 和 SSR 冒烟断言；更新契约用例并重录 `test/contract/golden/contract.golden.json`（388 条）。不新增迁移，不改变任务等级或既有编辑/验收权限。
5. **测试证据**：`test/api/task-visibility.spec.ts` 覆盖成员可见性、改派/归档恢复、跨组织边界、通知/SSE、导入去重和跨页排序；浏览器实测桌面与 390×844 移动端任务页，排序菜单、URL 持久化和重置均可用。
